## 5. EBS Storage Administration

### Work completed

- Created and attached a separate 3 GiB EBS volume to each EC2 instance.
- Used `lsblk` to identify the newly attached disks.
- Confirmed that `/dev/nvme0n1` was the root disk and `/dev/nvme1n1` was the additional data disk on each instance.
- Created an `ext4` filesystem on each new data disk.
- Created the `/data` mount directory.
- Mounted each EBS volume at `/data`.
- Added UUID-based mount entries to `/etc/fstab`.
- Reloaded systemd after modifying the filesystem configuration.
- Verified the mount configuration with `findmnt` and `mount -a`.

### Storage layout

| Instance | Data device | Volume size | Mount point |
|---|---|---:|---|
| `ip-172-31-13-65` | `/dev/nvme1n1` | 3 GiB | `/data` |
| `ip-172-31-3-12` | `/dev/nvme1n1` | 3 GiB | `/data` |

**Total additional storage:** 6 GiB across two independent EBS volumes.

### Commands used

```bash
lsblk
sudo mkfs.ext4 /dev/nvme1n1
sudo mkdir -p /data
sudo mount /dev/nvme1n1 /data
sudo blkid /dev/nvme1n1
sudo cp /etc/fstab /etc/fstab.bak
sudo nano /etc/fstab
sudo systemctl daemon-reload
sudo findmnt --verify
sudo mount -a
findmnt /data
df -h /data
```

The `/etc/fstab` entry was configured using each server's own filesystem UUID:

```text
UUID=<filesystem-uuid> /data ext4 defaults,nofail 0 2
```

The actual UUID must be different where the underlying volumes have different UUIDs.

### Warning encountered

After editing `/etc/fstab`, the system displayed a warning that systemd was still using the previous configuration.

**Resolution:** Ran `sudo systemctl daemon-reload` and repeated the mount verification commands. Both servers subsequently reported that their mounts were working.

**Current verification status:** The disks are formatted and mounted, and the mount configuration has been checked. A reboot-based persistence test remains pending.

## 7. Learning About tmux

### What I learned
- `tmux` is a terminal multiplexer that allows multiple terminal sessions and windows to run within one terminal.
- Sessions can remain active even after disconnecting from SSH, allowing work to continue on the server.
- Windows and panes help organize multiple tasks, such as monitoring logs, running commands, and checking application status.

### Important commands
```bash
# Start a new session
tmux new -s devops-practice

# List sessions
tmux ls

# Detach from the current session
Ctrl + B, then D

# Reattach to a session
tmux attach -t devops-practice

# Create a new window
Ctrl + B, then C

# Switch between windows
Ctrl + B, then N

# Kill a session
tmux kill-session -t devops-practice
```

### Key learning
`tmux` is useful for long-running DevOps tasks, server troubleshooting, log monitoring, and maintaining terminal sessions during SSH disconnections.

## 8. Learning About Amazon Route 53

### What I learned
- Amazon Route 53 is AWS's scalable DNS and domain-name service.
- DNS translates domain names, such as `example.com`, into the IP addresses or endpoints used to reach services.
- Route 53 can route a domain to an Application Load Balancer, allowing users to access an application through a domain name rather than an ALB DNS hostname.
- Route 53 supports routing policies such as simple, weighted, latency-based, failover, and geolocation routing.
- Health checks and routing policies can help direct traffic according to configured conditions.

### Connection to today's project
Today's Node.js application runs on two EC2 instances behind an Application Load Balancer. Route 53 can be used to create a DNS record that points a custom domain or subdomain to the ALB.

**Traffic flow:**

`User → Domain name (Route 53) → Application Load Balancer → EC2 instances → Node.js application`

### Key learning
Route 53 provides DNS-based name resolution and routing, while the ALB distributes incoming application traffic across registered targets.
