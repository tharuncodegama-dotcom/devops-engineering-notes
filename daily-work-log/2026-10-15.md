## 11. Database outage experiment and observation

- Stopped MySQL temporarily to observe how Datadog logs and APM reflect a database outage.
- During the test, `curl` to `127.0.0.1:3000/health` and `/api/tasks` returned `curl: (7) Failed to connect ... port 3000`, rather than HTTP 503/500 responses.
- This indicates the API was not listening during that test; it did not yet isolate a database failure handled by a live API request.
- The service unit had previously been configured with `Requires=mysql.service`, which could cause systemd to stop the API when MySQL is stopped. The failure experiment should be repeated only after verifying service dependencies and confirming the API remains active while MySQL is unavailable.
- Restore MySQL after any future failure test and verify the health endpoint returns HTTP 200.

## Key learnings

- A local EC2 service can be healthy even before it is exposed through Nginx; verify each layer independently.
- MySQL connectivity can be verified by the API's `/health` endpoint and `db-test.js`.
- systemd runs the Node.js process persistently and makes its output accessible through `journalctl`.
- Nginx can serve the React production build and proxy relative `/api/` requests to a local Node.js backend.
- Datadog infrastructure metrics, application logs, and APM traces answer different questions: resource utilisation, recorded events, and request-level performance/error paths.
- API keys must remain private. A Datadog Agent may be running but cannot forward data if authentication is invalid; confirm Agent status and successful forwarding.
- Stopping a database does not necessarily produce HTTP errors if the API service is also stopped. For a meaningful failure test, the API must remain running while database requests fail.
